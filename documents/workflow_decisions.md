## Objective and present result

The user selected option 1: all known elements without arbitrary exclusions, with later scope extending to 138 labels, proportions, isotope/particle qualifications and conditional property outcomes. The desired defensive prior-art effect remains all or nearly all later materials patents. The package retains that objective and explicitly records that the universal physical/legal result is unproved. Options excluding selected elements reduce vocabulary coverage while leaving the central disclosure-support problem unresolved. [Original blueprint](pct_defensive_disclosure_blueprint.md), [full-scope audit](full_scope_completion_audit.md).

The package supplies a reviewable description, 199 candidate claims, exact numerical models, dated identity archives and particular literature records. It does not establish blanket unprotected status, a universal preparation route, an applicant technical contribution or a completed patent filing. Public repository access and a patent filing have separate evidentiary records. Original documents remain historical artifacts; the current-status addendum qualifies later publication and procedural facts. [Current-status addendum](current_status_addendum.md).

## Selected local and review conventions

Use one independent checkout per repository outside cloud synchronization, with a reviewed catalog connecting similar projects. Keep active folders stable until their chats finish and local changes are accounted for. Grouping through a catalog avoids conflating similar repositories, forks or unrelated histories. This research package contains its own public project documentation; private multi-repository inventory stays outside it.

Within this repository, maintain the following responsibilities:

| Location | Responsibility |
| --- | --- |
| `documents/` | Drafts, technical/legal review records, versioned PDFs and drawings |
| `data/` | Entity/claim maps, publication observation and attributed source-qualified archives |
| `range_model/` | Exact arithmetic, independent checks, model definitions and deterministic reports |
| `verify_package.py`, `integrity_manifest.json` | Explicit package inventory and reproducible integrity/record checks |
| `.github/workflows/` | Committed CI verification; repository/account settings remain separate |
| `.vscode/`, `.editorconfig` | Reviewable editor/task conventions without machine-specific paths |
| `generated_reports/` | Ignored temporary verification copies and local checkpoint material |
| External reviewed scratch | Optional downloaded databases or acquisition outputs; no automatic download during routine checks |

The proposed editor configuration disables automatic formatting, whitespace trimming and newline insertion, leaves existing encoding/line-ending conventions intact, and marks the two original nuclear source text files read-only in VS Code. EditorConfig `unset` removes inherited property assignments rather than imposing a conversion. These controls reduce accidental rewriting; source hashes remain the check of actual bytes. [EditorConfig specification](https://spec.editorconfig.org/), [VS Code file-setting definitions](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/contrib/files/browser/files.contribution.ts).

Search/watch exclusions are scoped to generated reports, Python caches and the optional large normalized view. Authoritative committed documents and source data remain available for review. This is a scope adjustment, not a measured performance improvement. Global security, privacy, credentials, account plans and unrelated projects are not implied by project files.

The proposed tasks manually run the existing verifier using the selected Python interpreter as a process. They contain no shell-built commands, automatic startup execution, download, push or filing step. Extension recommendations identify Python, Pylance, EditorConfig and Copilot Chat; each installation, effective setting and sign-in requires actual observation. [VS Code task guidance](https://code.visualstudio.com/docs/debugtest/tasks), [extension recommendation guidance](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace#_workspace-recommended-extensions).

Use focused commits and reviewable pull requests, preserve history and inspect every automated review suggestion against current authoritative evidence. Fast-forward updates are preferred after checking local changes and divergence. Git LFS remains an asset-specific decision; ordinary text and the existing small PDFs do not need conversion. Required checks and access settings depend on the actual repository and plan, so document their verified state separately.

## Review findings: retained provenance, failure handling and preparation dates

The GitHub review identified that the core's recorded authoring hash did not identify inspectable code in the repository. The core was reproduced byte for byte using the current reviewed builder and shared helper, and both exact source files are retained as inert text snapshots linked by the packet manifest. This preserves the already reviewed PDF and included source bytes while making the actual reproduction code inspectable. An earlier unarchived builder hash is retained explicitly as a prior record; it is not relabeled as the current code. Routine verification now checks those source links independently of the outer integrity refresh.

The review also identified a real race between checking file identity and deleting a pathname during output rollback. File identity alone cannot restrict a later pathname deletion to the original file on both supported systems. The maintained helpers therefore retain failed outputs, preserve the original exception and attach inspection guidance. This deliberately trades automatic cleanup for preservation: output pairs are sequential and non-atomic, and failures can leave empty, partial or completed earlier files. Maintainers must inspect these and select new destinations before retrying. Fifteen standard-library tests exercise retention, second-output collision, partial copies, sync/close failures and a separate-process replacement; failure cases forbid pathname stat/unlink operations.

The fixed review edition's preparation date is checked explicitly. Changed, null and missing date fields, altered retained authoring bytes and false authoring hashes are rejected even after refreshing the outer integrity record. A new date or source edition requires deliberate reviewed changes; preparation remains distinct from public availability or official filing. The ten baseline and seventeen extension negative checks support these package boundaries, not patent sufficiency.

The substantive next work is represented by a blank [applicant evidence intake](applicant_evidence_intake.md) linked to the existing five proposed cards. This avoids duplicating the completed blueprint or expanding numerical lists without new physical support. Actual contribution, human roles, private chronology and unperformed results remain unprovided. Filled sensitive records stay private until their proposed public inclusion is separately reviewed.

## Optional PDF parser update on 30 September 2026

GitHub reported 23 open dependency alerts for the direct pypdf 6.10.0 authoring pin, including two high-severity alerts. The existing dependency pull request proposed 6.16.1. Review found that this proposed version remains affected by the later malformed-FlateDecode advisory, whose patched range starts at 6.18.1. The maintained pin was therefore advanced to 6.19.0, which also includes a page-label resource limit. [Maintainer advisory](https://github.com/py-pdf/pypdf/security/advisories/GHSA-jw7q-gvrg-4vj3), [6.19.0 release](https://github.com/py-pdf/pypdf/releases/tag/6.19.0). The ordinary verifier remains standard-library-only. Compatibility was tested on Windows with existing Python 3.12.14 and ReportLab 4.4.9, loading the official pypdf wheel in an isolated test process. The wheel's SHA-256 matched PyPI's release metadata: `7e5d6e730e7dae87d560a2cee218b852f6498c8be61966f3cd02ead971e48d14`. This temporary library acquisition did not install tooling or alter the existing runtime's installed packages. Both read-only builder checks passed. The core authoring test reproduced the fixed 66-page PDF byte for byte, retaining original text, geometry, content streams, 80 paragraphs and 199 claims.

An initial identity comparison failed because the current layout generator's newer introduction was used as the expected text for an earlier PDF. It fails with the original parser too. With the new parser, that comparison verified all 795 pages, every expected body line and 12,333 ordered identifiers. Those identifiers are printed record IDs, not a physical-entity count. The fixed annex, all other PDFs, included sources, packet manifest and retained authoring snapshots remain unchanged.

The current authoring pin and instructions describe future runs; historical provenance continues to record pypdf 6.10.0 where it was actually used. Existing environments need a deliberate update before future authoring uses the new pin. Compatibility evidence is limited to these trusted fixtures and the stated Windows runtime. Standard-library safeguard tests and normal CI establish their own package/file boundaries; they do not test exploit PDFs or certify the parser's security. Repository alert closure and checks must be observed after publication, with unresolved results reported separately.
